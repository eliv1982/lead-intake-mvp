# Lead Intake MVP

Lead Intake MVP is a compact backend service for automated lead intake.
It receives webhook-style requests, validates payloads, stores leads in SQLite, and writes a best-effort diagnostic event log.
The project demonstrates a practical API automation pipeline for learning and portfolio use — it is an educational MVP, not a production service.
Core flow: **Webhook/API -> Validation -> SQLite -> Event Log (best-effort)**.

---

## Название проекта

**Lead Intake MVP (Webhook -> SQLite -> Event Log)**

## Описание

Мини-сервис для автоматизации приёма лидов.
Эндпоинт `POST /lead` принимает заявку, валидирует данные, сохраняет запись в SQLite и (по возможности) фиксирует диагностическое событие в `events.log`.

## Бизнес-проблема

В небольших командах заявки часто обрабатываются несистемно:

- обращения приходят из разных источников и теряются;
- менеджер узнаёт о новой заявке слишком поздно;
- контактные данные хранятся хаотично (чаты, таблицы, заметки).

Из-за этого снижается скорость реакции и теряются потенциальные клиенты.

## Решение

Сервис даёт единый и предсказуемый канал приёма заявок:

- `POST /lead` принимает структурированный JSON;
- валидация проверяет обязательные поля (в первую очередь `contact`) и скромные ограничения длины полей;
- данные сохраняются в SQLite (`data/leads.db`);
- после успешного сохранения делается попытка записать событие в лог (`logs/events.log`) — best-effort, не гарантированная транзакционно;
- ошибки валидации и сервера возвращаются с корректными и документированными в OpenAPI HTTP-кодами (400 / 500).

## Стек технологий

- Python 3.12 (проверено на этой версии; см. `requirements.txt` для диапазонов версий пакетов)
- FastAPI
- Uvicorn
- SQLite
- Pydantic 2
- Logging (стандартная библиотека)
- Тесты: `unittest` (стандартная библиотека) + `fastapi.testclient.TestClient`

## Возможности

- `POST /lead` — создание лида
- `GET /health` — проверка доступности сервиса (liveness, не проверка БД)
- валидация входящих данных, включая ограничения длины полей
- хранение заявок в SQLite (дубликаты `contact` допускаются, дедупликации нет)
- best-effort диагностическое логирование событий в файл
- обработка ошибок с явным и документированным контрактом (400 и 500 в OpenAPI, без «случайного» 422)
- компактный набор автоматических тестов, изолированный от реальных `data/leads.db` и `logs/events.log`

## Установка

Требуется Python 3.12.

1. Клонировать репозиторий:

```bash
git clone <your-repo-url>
cd lead-intake-mvp
```

2. Создать виртуальное окружение:

```bash
python -m venv .venv
```

3. Активировать виртуальное окружение:

- PowerShell:

```powershell
.venv\Scripts\Activate.ps1
```

- Bash:

```bash
source .venv/bin/activate
```

4. Установить зависимости приложения:

```bash
pip install -r requirements.txt
```

Для запуска тестов дополнительно нужны dev-зависимости (`httpx`, требуется `fastapi.testclient.TestClient`):

```bash
pip install -r requirements-dev.txt
```

## Запуск

Запуск сервера разработки:

```bash
uvicorn app.main:app --reload
```

После запуска:

- базовый URL: `http://127.0.0.1:8000`
- Swagger UI: `http://127.0.0.1:8000/docs`
- OpenAPI JSON: `http://127.0.0.1:8000/openapi.json`

Пути к БД и логу (`data/leads.db`, `logs/events.log`) — относительные и предполагают запуск из корня репозитория, как описано выше.

## Использование API

### `POST /lead`

Пример JSON-тела запроса:

```json
{
  "name": "Ирина",
  "contact": "+79990000000",
  "source": "landing",
  "comment": "Хочу консультацию по тарифам"
}
```

Обязательное поле — только `contact` (строка, после обрезки пробелов не должна быть пустой). `contact` — это универсальная строка контакта (телефон, email, мессенджер и т.д.), полноценной валидации формата email/телефона сервис не делает.

#### Ограничения длины полей

| Поле      | Максимальная длина |
|-----------|--------------------|
| `contact` | 255                |
| `name`    | 200                |
| `source`  | 100                |
| `comment` | 2000               |

Это осознанно простые ограничения MVP-уровня (чтобы отсекать бессмысленные payload'ы в десятки тысяч символов), а не полноценная бизнес-валидация.

### `GET /health`

Простой health-check (liveness сервиса, не проверка доступности БД):

```bash
curl http://127.0.0.1:8000/health
```

## Примеры запросов PowerShell и curl

### PowerShell

```powershell
$body = @{
  name    = "Ирина"
  contact = "+79990000000"
  source  = "landing"
  comment = "Хочу консультацию по тарифам"
} | ConvertTo-Json

Invoke-RestMethod `
  -Uri "http://127.0.0.1:8000/lead" `
  -Method Post `
  -ContentType "application/json" `
  -Body $body
```

### curl

```bash
curl -X POST "http://127.0.0.1:8000/lead" \
  -H "Content-Type: application/json" \
  -d "{\"name\":\"Ирина\",\"contact\":\"+79990000000\",\"source\":\"landing\",\"comment\":\"Хочу консультацию по тарифам\"}"
```

## Примеры ответов 200 / 400 / 500

### 200 OK (успешно)

```json
{
  "id": 1,
  "message": "Lead saved successfully."
}
```

### 400 Bad Request (ошибка валидации)

Все ошибки валидации запроса (включая некорректный JSON, отсутствующий `contact`, неверный тип поля или превышение длины) намеренно возвращаются как `400`, а не как стандартный FastAPI/`422`. Это отражено и в сгенерированной OpenAPI-схеме (`/openapi.json`) — для `POST /lead` там нет автоматического `422`, только `200`, `400` и `500`.

```json
{
  "detail": "contact: Field required"
}
```

или

```json
{
  "detail": "contact: Value error, Field 'contact' is required and must not be empty."
}
```

### 500 Internal Server Error

Известная ошибка SQLite (например, недоступна БД):

```json
{
  "detail": "Database error."
}
```

Любая другая непредвиденная ошибка сервера перехватывается общим обработчиком (HTTP-middleware в `app/main.py`, а не `@app.exception_handler(Exception)` — см. комментарий в коде: последнее переисключает обработку в Starlette `ServerErrorMiddleware`, который всегда повторно выбрасывает исключение после отправки ответа, а под реальным Uvicorn это может привести к преждевременному закрытию соединения и обрыву тела ответа) и возвращается в том же общем JSON-формате, без деталей исключения, SQL или путей файловой системы:

```json
{
  "detail": "Internal server error."
}
```

## Тесты

Тесты используют только стандартную библиотеку `unittest` и `fastapi.testclient.TestClient` — отдельный тест-раннер не требуется.

Перед первым запуском тестов установите dev-зависимости:

```bash
pip install -r requirements-dev.txt
```

Запуск полного набора тестов из корня репозитория:

```bash
python -m unittest discover -s tests -t .
```

(Важно использовать именно эту форму — с `-t .` — чтобы `tests/__init__.py` гарантированно выполнился раньше `app.main` и корректно подменил пути к БД и логу на временные. Тесты запускаются как пакет `tests.*`, поэтому `python -m unittest discover -s tests` без `-t .` тоже сработает, но `-t .` — самый надёжный вариант.)

Тесты покрывают как минимум:

- `GET /health`;
- валидный лид (минимальный и полный payload), сохранение в SQLite, полученный id, одно диагностическое событие в логе;
- ошибки валидации: отсутствующее тело, невалидный JSON, `null`, список/скаляр вместо объекта, отсутствующий/`null`/неверного типа `contact`, пустой после обрезки `contact`, неверный тип опционального поля, превышение длины полей;
- явную проверку того, что дублирующиеся `contact` сейчас допускаются и получают разные `id` (без дедупликации);
- ожидаемую ошибку SQLite и непредвиденное исключение — оба должны приводить к общему JSON-контракту 500;
- приоритет обработчиков: неизвестный путь (`404`), неподдерживаемый метод (`405`) и явно выброшенный `HTTPException` не подменяются общим catch-all на `500`;
- best-effort природу логирования: сбой записи в лог (включая исключение из самого вызова логирования) не откатывает уже закоммиченный лид, приводит к общему `500` с тем же JSON-контрактом, и — явной прямой проверкой, а не только по побочному эффекту — SQLite-соединение всё равно закрывается (`app/main.py::create_lead` закрывает соединение в `finally`, а не полагается на сборку мусора);
- содержимое `/openapi.json` (документированные коды ответов и схемы для `/health` и `/lead`);
- реальный сетевой regression-тест (`tests/test_uvicorn_regression.py`): поднимает приложение в отдельном процессе через документированный `uvicorn app.main:app` (не `TestClient`) и проверяет, что непредвиденное исключение отдаёт полный JSON `500` по настоящему HTTP-соединению, без обрыва тела ответа и без зависания;
- корректную очистку временных файлов на Windows (`tests/test_cleanup.py`): реальный subprocess-regression-тест запускает настоящий `EventLoggingTests` в дочернем процессе и явно сверяет список временных директорий `lead_intake_mvp_tests_*` до/после — а не только полагается на код выхода дочернего процесса, так как Python игнорирует исключения из `atexit`-колбэков для кода выхода.

Тесты используют временную директорию для БД и лога и **не изменяют** `data/leads.db`, `logs/events.log` или любые другие файлы репозитория.

## Позиционирование в портфолио

Проект можно использовать как учебный и практический MVP-кейс для откликов на стажировки и фриланс-заказы:

**Webhook -> DB -> Event Log**

Он демонстрирует:

- проектирование API и валидацию данных;
- хранение данных и работу с SQLite;
- best-effort событийное логирование;
- аккуратную и документированную (через OpenAPI) обработку ошибок;
- компактный автоматический тест-сьют, изолированный от реальных данных;
- ориентацию на бизнес-задачу автоматизации приёма лидов.

## Принятые ограничения MVP

Эти решения приняты осознанно и не являются недоработкой:

- **нет аутентификации** — эндпоинты открыты, это локальный учебный MVP;
- **дублирующиеся лиды разрешены** — по одному и тому же `contact` можно создать сколько угодно записей, уникального ограничения на `contact` нет и идемпотентности запросов нет;
- **`GET /health` — это liveness, а не readiness БД** — успешный ответ не означает, что SQLite доступна;
- **SQLite синхронный** — `sqlite3` используется напрямую, без пула соединений и без async-драйвера;
- **`contact` — это просто непустая строка** — сервис не валидирует формат email или телефона и не претендует на это;
- **лог событий — best-effort диагностика, а не audit trail** — коммит в БД может успешно завершиться, даже если последующая запись в `logs/events.log` не удалась. Это возможно в двух случаях: (1) процесс упал между коммитом и записью лога — тогда клиент вообще не получает ответа, а лид сохранён в БД без соответствующей строки в логе; (2) сам вызов логирования выбросил исключение в рамках обработки запроса — тогда клиент получает штатный общий `500` (`{"detail": "Internal server error."}`, тот же общий JSON-контракт, что и для любой другой непредвиденной ошибки), но лид уже сохранён в БД и откат не выполняется, так как запись в лог не является частью транзакции. Это осознанно выбранное и зафиксированное тестом поведение (`tests/test_api.py::EventLoggingTests`), а не недоработка;
- **неизвестные поля в запросе игнорируются** — модель не настроена на запрет дополнительных полей;
- **пути к БД и логу относительные** — корректно работают при запуске из корня репозитория, как описано в разделе «Установка»/«Запуск».
